# 19来源工单的两阶段调度

本页维护19来源分支的输入与底层调度；业务判定只读[19来源规则](manual19-workorders.md)。复用 `mcp_session.py` 已登录的标准MCP会话，助手在同一进程中顺序调度；不建立另一个E10连接、不通过界面操作。只有技能/代码更新任务时使用离线回放，不登录或生成业务单据。

## 1. 形成行级范围

用本轮完整钉钉采集及已确认参数写范围JSON。所有路径相对于 `mcp_session.py --work-dir`；范围、快照和输出在工作目录中，不能放在技能目录。范围根字段：

| 字段 | 内容 |
| --- | --- |
| `target_url` | 本次钉钉文档URL |
| `source_snapshot` | 本轮完整采集JSON的相对路径；保持只读 |
| `plant_name` | 已确认工厂全名 |
| `selection_rules` | 本轮 `excluded_1_v_name_keywords`、`excluded_1_h_name_keywords`，沿用已确认规则 |
| `feature_overrides` | 可选。键为`工作表:实际行号`，值含`item_code`、`feature_code`、`basis`；只有用户明确提供的覆盖才写入 |
| `excluded_rows` | 可选。`[{"sheet":"实际工作表","row":实际行号}]`；完整原因及单据身份另留本轮排除记录 |
| `specs` | 本轮确需新增的全部行，按实际行顺序；已有工单不得作为空白行重开 |

每个spec包括sheet、row（从1开始，含表头）、source_no（实际“单号”）、source_plan_date（排产原始文本）和arguments。普通表另存真实sheet_id，row为真实工作表行，不得带record_id；AI表另存真实record_id，row仅为本地矩阵位置。`arguments`必须完整包含：

```text
item_code, feature_code, plant_id, quantity,
doc_date, start_date, complete_date, reference
```

日期均为 `yyyy-MM-dd`，由主代理按本轮日期/排产及用户要求确定，不由助手猜年份。工厂ID通过当前主数据取得。数量可在范围文件中用精确数字文本，助手验证可以无损传入现行MCP数值参数；不合并相同行、不四舍五入。

reference沿用稳定格式：`包装计划:文档节点标识:工作表:19来源单号:品号:完整特征码:标准数量:同信息序号`。标准数量去无意义尾零，不用科学计数；同信息序号按完整当前表内的来源单号、品号、有效特征码、数量计数，包含已有工单行，不能按当前空白行重新编号。文档节点标识取URL `/i/nodes/` 后的实际值，不用本轮随机目录名。助手会重新计算并核对，长度上限200。

## 2. 同会话准备并核对

发送一行：

```json
{"job":"manual_prepare","scope":"manual19-scope.json","directory":"manual19-run"}
```

目录必须尚不存在。助手依次进行：

- 核对全部指定行的真实单号、三字段、排产原值、空白工单格、稳定序号、行级覆盖及排除范围。
- 唯一解析当前5101类型；按品号、完整特征、数量、工厂和日期的完全相同组做一次只读预览。所有组通过后才逐行准备。
- 每行调用原 `e10_prepare_manual_workorder`；逐项核对当前主资料、完整原生BOM及仓库/储位、产出、人员、生产部门、工作中心、日期、初始状态和工艺管理。操作ID、工单ID及子件ID逐行独立。
- 第一个错误立即停止并保存证据，后续行不继续准备；此阶段不保存或审核正式单据。

摘要只返回数量、唯一预览组数、`prepared.json`路径和SHA256。完整预览、每行草稿及原值留在阶段目录。主代理核对完整范围和检查结果，确认没有把未授权行、已有单据或被排除行混入。

source_check采用本轮最新完整快照，身份及受保护字段按[钉钉契约](dingtalk-mcp.md#快照生命周期)，不因prepare重新在线采集。

## 3. 批内逐单保存与核对

确认范围已获用户授权、完整准备和写前快照检查通过后，发送：

```json
{"job":"manual_create","directory":"manual19-run","approved_sha256":"本次prepared.json的实际SHA256","source_check":"manual19-before-save.json"}
```

必须是准备时同一个MCP会话。助手检查原范围/证据哈希、全部草稿、写前来源、从第一张开始准备算起的25分钟门槛及当前认证；认证失效时不自动登录、不开始保存。大批量按30分钟内存有效期控制明确批次，首次正式写前仍核对本轮完整业务范围，不能改变每行数量或稳定序号。随后在一次调度中逐张执行：

1. 独占写入`commit-started-操作ID.json`及检查点`in_flight`，调用原commit一次；检查成功回执的产品、特征、数量、单位、部门、人员、来源、日期、全部子件与产出。
2. 创建阶段只保存工单并产出逐行bindings与成功回执，不审核。统一审核由 workorder_branches.py 在两个来源分支创建门槛通过后顺序执行。
3. 每个对象必须得到创建成功回执；明确零新增也须返回显式成功回执。缺回执、失败、超时或unknown均停止，不自动重试。
4. 输出创建完成回执及行级`bindings`，包含真实来源、三字段、reference、工单号与ID。两分支创建回执齐全并统一审核完成后，才进入工单匹配。

批内由助手串行完成，进度和终端输出按[执行约定](performance.md#输出预算)。BOM、当前主资料指纹、重复来源及单据版本检查继续由原MCP逐单执行，未使用BOM缓存绕过校验。保持两个阶段之间的完整模型核对，减少的是逐单聊天/终端轮询。

## 停止、记录和接续

- 准备失败、正式保存失败、返回内容不符或异常都立即停止后续业务；保留每单回执、`failure-*.json`、started与in_flight。审核错误由统一审核阶段记录。
- 同一执行检查点不能自动重跑，包括部分成功。先读取操作状态及受影响实际单据，记录已成功、已审核及未完成对象，再按明确证据接续；不删除标记，不换reference或目录绕过未知结果。
- 只读预览/准备阶段未开始正式写入的认证问题可由主代理显式恢复。恢复后须核实仍是同一内存会话且草稿未过期；新会话只能重新准备已经确认未保存的对象。
- 本分支calls.jsonl记录SDK耗时及回执路径，会话根mcp-calls.jsonl记录统一时间线；度量边界见[执行约定](performance.md#度量边界)。
- 工单及领料回填继续用原匹配技能。普通四字段不变；19来源使用真实bindings合并完整计划，不伪造需求单号。用户清空/移动的行不恢复旧值；正常提交后不增加写后读回。
